# 共用操作规则

这些规则来自 deepcoffee-dev 的实际使用，继续由本 skill 维护。

## 每次实际操作前的维护检查

沿用原横切规则：执行 DeepCoffee 的交付、部署、账号或知识库等实际任务前，先运行一次 cleanimg 的 check；本次已完成检查就复用结果。沿用 [maintenance.md](maintenance.md) 的既有常规维护安排：有积压时，在用户已确认的常规维护范围内执行清理并报告数量；数字异常大先确认。当前用户明确要求只读或限制写入时，以当前请求为准。

检查失败，例如相应版本尚未部署或网络失败，不阻塞主任务；说明后继续。此安排沿用既有决定，不另建 Cloud Scheduler。仅审阅或编辑本 skill 不触发维护脚本。

## 已有交付、验收与版本规则

- PR/合并和部署分开。只有用户明确说上线、部署、发版时才执行生产部署。
- 交付方式先按风险分流：低风险直接提交 `main`，中高风险或用户明确要求审查时才拉分支开 PR。
- PR 分支合并后要顺手删除远端分支；不要让已合并分支长期留在远端。
- deploy 的 Codex 完成条件是发布动作成功触发、必要命令正常结束且 CI 通过；线上状态和最终验收不属于 Codex 的检查范围。
- 默认减少本地大范围测试，主要依赖针对性本地检查与 PR/CI；不要自行做线上验证。
- 线上页面、Vercel 状态、Cloud Run 状态和生产渲染全部交给用户，但必须清楚说明用户需要检查什么。
- 如果 PR、合并、push、CI 或部署命令因为权限、网络或环境限制无法完成，要把状态说清楚；不要把“已触发发布”描述成“线上已完成”。
- 版本号更新要按发布语义判断，不要把“修 bug”自动等同于 patch：
  - patch（例如 `0.23.0` -> `0.23.1`）只用于修当前最新版本引入的回归、同一版本的小热修、纯元数据 / 文档 / 很小兼容修正。
  - minor（例如 `0.23.0` -> `0.24.0`）用于新的用户可见能力、产品流程变化、AI 行为改进，或修复长期存在但这次才解决的用户可见问题。
  - major 暂不主动使用，除非有明确破坏性 API / 数据兼容变更并经用户确认。
  - 如果不确定这是当前版本回归还是长期问题，先问用户，不要擅自创建很小的 patch 版本。
